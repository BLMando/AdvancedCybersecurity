### Opzione A: Modificare la Query Splunk (SPL) — Altamente Consigliata per Performance                 
                                                                                                          
  Splunk è un motore di ricerca e analisi indicizzato estremamente potente. Chiedergli di calcolare       
  metriche storiche complesse direttamente in fase di query è molto più efficiente che scaricare migliaia 
  di log grezzi in Python per poi elaborarli.                                                             
                                                                                                          
  Ecco alcune metriche storiche avanzate che puoi calcolare direttamente in SPL (Splunk Search Processing 
  Language):                                                                                              
                                                                                                          
  #### 1. Time Decay (Decadimento Temporale dei Rischio)                                                  
                                                                                                          
  Un attacco o un'anomalia avvenuta 14 minuti fa dovrebbe pesare meno di una rilevata 10 secondi fa. In   
  SPL possiamo calcolare un punteggio pesato in base all'età dell'evento:                                 
                                                                                                          
    search index=zta_snort src_addr="172.20.0.5" earliest=-15m                                            
    | eval eta_minuti = (now() - _time) / 60                                                              
    | eval peso_anomalia = case(eta_minuti <= 2, 1.0, eta_minuti <= 5, 0.5, 1, 0.1)                       
    | stats sum(peso_anomalia) as weighted_anomaly_score                                                  
                                                                                                          
  In Python: Il forwarder riceverà un punteggio pesato (es.  2.5  invece di un semplice conteggio intero  
  5 ), rendendo il calcolo del  risk_boost  molto più accurato.                                           
                                                                                                          
  #### 2. Anomaly Detection rispetto alla Baseline Utente                                                 
                                                                                                          
  Invece di contare semplicemente le query recenti, possiamo verificare se la frequenza attuale devia     
  significativamente dalla media storica dell'utente (es. calcolando la deviazione standard o confrontando
  gli ultimi 15 minuti con le ultime 24 ore):                                                             
                                                                                                          
    search index=zta_envoy user="mario.rossi" earliest=-24h                                               
    | bucket _time span=15m                                                                               
    | stats count as query_per_finestra                                                                   
    | stats avg(query_per_finestra) as media, stdev(query_per_finestra) as dev_std                        
                                                                                                          
  Possiamo unire questa ricerca a quella degli ultimi 15 minuti per determinare se il comportamento       
  attuale è uno scostamento anomalo (es. Z-Score > 2).

### Diagramma di Flusso delle Operazioni

```mermaid
    sequenceDiagram
        autonumber
        actor Utente as Utente (Browser)
        participant Agent as ZTA Local Agent (:9090)
        participant Flask as Flask Backend (app.py)
        participant Envoy as Envoy Proxy (:10000)
        participant OPA as OPA Engine (:9002)
        participant Fwd as OPA-Splunk Forwarder (:5000)
        participant Splunk as Splunk Enterprise
        participant Mongo as MongoDB

        Utente->>Flask: 1. Click "Invia Query mTLS" (Payload query + JWT OIDC)
        Note over Utente, Agent: Se Hardware-Bound:<br/>Javascript richiede Touch ID/Hello<br/>e ottiene il JWT OIDC dall'Agente locale.

        rect rgb(20, 30, 45)
            Note over Flask: RLS & Vista Translation
            Flask->>Flask: Decodifica JWT, estrae il Ruolo<br/>e mappa la collezione in una vista RLS<br/>(es. clinical_records -> v_clinical_doctor)
        end

        Flask->>Envoy: 2. Invia query mTLS (con Client Cert e JWT)

        rect rgb(30, 20, 20)
            Note over Envoy: Intercettazione PEP L4/L7
            Envoy->>Envoy: Termina mTLS (Valida contro ca.crt)<br/>mongo_proxy decodifica il comando BSON
            Envoy->>OPA: 3. gRPC CheckRequest (Metadati, Cert, Comando)
        end

        rect rgb(20, 40, 30)
            Note over OPA, Fwd: Valutazione Rischio in tempo reale
            OPA->>Fwd: 4. HTTP POST /api/stats (Chiamata sincrona http.send)
            Fwd->>Splunk: 5. Query REST Oneshot (Log degli ultimi 15m)
            Splunk-->>Fwd: Ritorna allarmi Snort, drop nftables, fallimenti Mongo, dinieghi Envoy
            Fwd-->>OPA: 6. Ritorna risk_boost aggregato
            OPA->>OPA: Calcola risk_score finale contro la soglia adattiva
        end

        OPA-->>Envoy: 7. gRPC CheckResponse (Decisione: ALLOW/DENY)

        alt OPA ALLOW
            Envoy->>Mongo: 8a. Inoltra connessione TCP (tcp_proxy)
            Mongo-->>Flask: Risultati della query (sulla vista RLS)
            Flask-->>Utente: Mostra i dati in Tabella / JSON
        else OPA DENY
            Envoy-->>Flask: 8b. Connessione TCP rifiutata
            Flask-->>Utente: Mostra Errore 403 (Accesso negato da OPA)
        end
```
